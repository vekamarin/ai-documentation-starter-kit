AIDLC

For V2, we flipped the model.

We adopted AIDLC, the AI-Driven Development Lifecycle, and adapted it to our project.

Primary input
Specifications
AI drafts, humans approve
Engine
AI
Generates the code
Output
Code
Derived from specs

Specs are the source of truth. When the code and the spec disagree, we fix the spec first.

What the industry now calls context engineering, applied to the whole project.

AI-DLC: open methodology introduced by AWS, 2025

AIDLC

Layered specs, written before the first feature

Business context
Personas, capability map, which user journeys matter first
57 ADRs
Architecture Decision Records: each choice and why we made it
6 capability specs
What each capability does, accepts, returns, and how it fails
Architecture
Principles, system boundaries, the data model
V1 forensics
What went wrong in V1, measured, with a target for each finding
Templates
For ADRs, capabilities and features, so every new spec has the same shape

The AI wrote the first drafts. We reviewed, corrected and approved every one.

Four weeks on the calendar, 11 days of actual work. Most of the wait was review turnaround. About 11,000 lines landed in the new repo's first commit, and code started the next day.

AIDLC

Don't dump all 11,000 lines into CLAUDE.md

You decide how your documentation is structured: what loads every time, and what loads on demand.

One giant instructions file (loaded on every prompt)
All 57 ADRs
All 6 capability specs
All 16 skills
Architecture
Noisy & expensive.
The rule that matters is buried.
Small files + pointers (loaded when the task needs them)
Short CLAUDE.md
1 skill
1 spec + its ADR
room for the actual task
Focused & fast.
Only relevant rules in view.

Keep CLAUDE.md short: just principles and pointers. Split the details into separate files so the AI only reads what relates to the current task.

More context isn't better. The right context, at the right time, is.

AIDLC

Organize context so the AI reads it in the right order

General things always loaded. Details only when the task needs them. Claude Code supports this out of the box:

AlwaysCLAUDE.md + @importsPrinciples, conventions, pointers to the specs
By path.claude/rules/*.md (paths:)Rules that apply only to matching files, e.g. migrations
By foldersrc/billing/CLAUDE.mdLoaded when Claude starts working in that folder
On match.claude/skills/*/SKILL.mdOnly name + description in context until a task needs it

A plain link to a spec is just text. If the AI must read it, import it or put it in a rule or skill.

AIDLC

Skills encode how you work

Specs say WHAT to build. Skills say HOW to work. A skill links to the spec, it never copies it.

.claude/skills/db-migrations/SKILL.md
1---
2name: db-migrations
3description: Use when creating or editing
4 SQL migrations or changing the schema.
5---
6# Database migrations
7- One migration per change. Never edit an applied one.
8- Never hardcode a schema name. One schema per tenant.
9- After pulling: npm run db:migrate
10- Why: see docs/decisions/adr-020.md
.claude/skills/
├ db-migrations/
├ seed-data/
├ ui-components/
├ testing/
├ git-workflow/
└ deployment/

V2 has 16 of these. Each is short and focused, and only loads when the work touches its area.

AIDLC

V1 failures became V2 guardrails

Before writing V2, we wrote a forensic analysis of V1. Each finding became an ADR.

V1 finding
Three data patterns: hardcoded, database, AI-generated. Nobody could tell what was real.
→
ADR-017 · Ban frontend mock files
One path only: seed → DB → API → UI. Source files with mock data: 93 → 2
V1 finding
Component bloat. The largest file reached 4,090 lines.
→
ADR-027 · 300-line component limit
Not perfect: our largest is 1,022. But files over 2,000 lines: 6 → 0
V1 finding
Multi-domain support bolted on later, across six migrations.
→
ADR-019/020 · Domain is configuration
Schema per customer, designed in from migration 001.

Practical Takeaway

Humans own the specs. AI can draft them.

Backup · if asked

"Doesn't research say AGENTS.md files don't help?"

What the study found

On SWE-bench, repository context files often did not improve success, and raised inference cost by 20%+.

What it measured

Isolated, historical bug fixes. Narrow patches where a general instruction file is mostly noise.

Why it fits this talk

Feature work is different: models drop sharply on multi-file features (FeatureBench). And the lesson is ours too: curate, don't dump.

"Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?", 2026 · FeatureBench, ICLR
